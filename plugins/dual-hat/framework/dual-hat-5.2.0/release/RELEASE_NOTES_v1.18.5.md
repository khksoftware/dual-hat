# Dual Hat 1.18.5 Release Notes

This compatible governance release adds one rule and one discoverability notice to `governance/GOVERNING_PRINCIPLES.md`. Neither changes a schema, an interface, a required field, or the repository layout, and no rule is renumbered or relocated.

Rule 36 -- survey before designing -- requires that, before designing a capability, proposing an approach another role is expected to act on, or asking the stakeholder to choose between designs, an agent establish from the system's actual current source whether the capability, or an adjacent one with settled semantics it should extend, already exists. Reading and searching the real code and artifacts is the evidence; memory of the system, a prior summary, and plausibility are not. The survey looks for the capability's behavior rather than only the name the requester or the agent happened to use for it, because the gap between the requester's word and the system's own vocabulary is precisely how an existing capability stays hidden. What was searched, and what was found or ruled out, is stated alongside whatever is proposed -- an unstated survey is indistinguishable from an unperformed one.

The rule is bounded by proportionality: for a small, local change, one targeted search, stated, discharges it. The obligation does not shrink to nothing because the change seems small, and it never expands into ceremony.

Where the capability already exists, the rule requires extending it and matching its established semantics rather than adding a second behavior under the same name, since every later reader would otherwise have to first discover which of the two they are looking at. Where it exists but is genuinely unfit, that is said explicitly against the real implementation rather than designed past in silence.

The failure rule 36 exists to prevent is not merely wasted effort. An option set assembled without a survey can be presented with full apparent rigor, and that presentation makes an uninformed question indistinguishable from a considered one. The stakeholder cannot audit a premise they were never shown, so a decision is spent on a question that should never have been asked. Where that has already happened, rule 36 requires the correction and the false premise to be stated to the stakeholder in the same turn the error is discovered, with the original framing kept visible in the record; where a genuine choice still remains among fit options, the question returns with the premise corrected. A correction is never a route to settling a matter the cardinal rules reserve to the stakeholder.

Rule 36 is distinct from rule 22 rather than redundant with it. Rule 22 forbids constructing a parallel implementation of a process this framework already governs -- it is about what is built; rule 36 is about what is proposed, and a proposal made without a survey precedes and causes the duplication rule 22 then has to forbid.

This release also removes a false status claim from rule 32's own closing sentence. That sentence still described rule 32 as drafted and committed pending independent review and not yet finally adopted -- a claim that stopped being true the moment rule 32's own review completed and it was adopted and released, and that nothing kept synchronized afterward. Because rule 32 bars an unadopted change from being slated for propagation, the published document was telling every adopter that its most-cited rule was an unadopted draft that had nonetheless been published, contradicting the changelog and release notes shipping in the same package. Shipping that alongside the new head notice would have compounded it: the notice points a reader at rule 32, and rule 32 then disclaimed its own adoption.

The sentence now reads only "This rule is itself a governance-rule change and is therefore subject to its own requirement." That keeps, in the present tense, the half that is true and durable -- rule 32 binds amendments to itself, now and in future -- and drops only the half that had gone stale. Writing the obligation in the past tense was considered and rejected: it would have stated as discharged something that is continuing, and would have left a provenance marker inside portable rule text that cannot cite its own evidence. Rule 32's operative requirement is unchanged and nothing else in it is reworded; the adoption fact stays recorded in the changelog and the 1.18.1 release notes, which own provenance. This is the same defect class as the pending-review markers rules 35 and 36 each carried and each had retired at adoption; a sweep of the framework for any other stale self-describing status marker of this kind found none remaining.

This release also repairs a structural misattribution between rules 33 and 34 in the same document. Rule 33 governs the stakeholder-to-Architecture-to-Engineering authority channel; rule 34 governs confirmed genuine test failures never being treated as ambient repository state. Two paragraphs squarely belonging to rule 33 -- the prohibition on a delegated agent treating a relayed claim of stakeholder authorization as verified consent, and that prohibition's incident citation -- were physically located inside rule 34's body, because the commit that introduced rule 34 inserted it into the middle of rule 33 and rule 33's tail was never moved back afterward. Any reader encountering them attributed rule 33's central prohibition to a rule about test failures.

Both paragraphs are relocated to the end of rule 33, where they began. This is a pure move: no sentence is reworded, nothing is merged into the surrounding paragraphs, no rule is renumbered, and rule 33's body is byte-identical to its form before the insertion that displaced it. What either rule requires is unchanged; only what each rule contains is corrected. A search for the same pattern elsewhere in the document -- a rule's closing paragraphs stranded under its successor by an insertion -- examined every commit that ever added a numbered rule to this document and found no other instance.

This release also adds a notice at the head of the same document. Rule 32 already requires that a change to that document's own rules be reviewed by an independent Architect before it counts as adopted, and states that committing the drafted text is not itself adoption -- but rule 32 sits well into the longest governance document in the framework, is not reachable from the required entry point or the canonical entry-point and domain indexes, and has no inbound cross-reference anywhere. For an adopting project outside the one where the requirement originated, it had no carrier that travels with the rules. The notice states the requirement plainly at the top and names rule 32 as the full statement that governs, so it can never be relied on against rule 32 itself. Renumbering was rejected as the alternative: it would silently invalidate several hundred existing rule-number citations.
