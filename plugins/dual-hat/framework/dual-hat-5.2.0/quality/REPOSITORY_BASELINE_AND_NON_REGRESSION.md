# Repository Quality Baseline and Non-Regression

An initial baseline is a Deep, evidence-supported review of tracked active source and behavior-affecting configuration. Archives are not active source; private content, credentials, ignored intake, and rights-controlled material are excluded except for minimal governed safety metadata. The review combines independent inspection, bounded static analysis, dependency inspection, direct CLI and focused/broad tests, failure cases, generated-output checks, detached committed-tree validation, secret/path scans, and platform preflight. Tools are proportionate, local, provenance-checked, and never upload repository content without separate authority.

The machine-readable baseline binds the commit, date, scope/exclusions, tier, platform profile, rule-source files/revisions/hashes, effective-plan hash, sealed work item and lifecycle, suppressed/replaced rules, methods/tool versions, meaningful metrics, risks, exceptions and trade-offs, findings/debt, evidence, disposition, and its own canonical hash. Trusted owning code derives this binding from the exact clean Git HEAD and reproducible governed profile, rule inventory, plan, seal, and handover files. A caller-supplied mapping is never authoritative; it can only be checked as an additional assertion against the derived state.

Acceptance makes the governed-state binding immutable. Historical comparisons verify the preserved accepted binding rather than pretending an old baseline describes the current checkout. The new candidate is independently bound to current primary state. Comparison reports invalid historical evidence, invalid candidate state, metric regression, new debt, new blockers, rule-policy change, and repository mismatch separately. Later reviews supersede rather than overwrite an accepted baseline.

For every future behavior-affecting handoff, Engineering reports affected baseline areas, tier and effective rule revision, applicability changes, new/resolved risk and debt, dependencies/security surface, material complexity or duplication, test changes, regressions, and proposed rationale. Architecture independently compares them. A material regression requires correction, a valid user override, explicit accepted debt, or separately governed architecture. Unknown high-risk regression state blocks acceptance.

When policy changes, preserve the historical rule set and compare under both historical and current contracts where material. Distinguish policy reclassification from code regression; suppression is not a fix. Rebaseline only for meaningful architecture/quality change, major remediation, milestone review, activated external rollout, or explicit Architecture authority. Never move the baseline merely to hide regression.
