# Continuity Closeout and Deferred Publication

Every new work order explicitly chooses lightweight continuity or full closure. Existing work orders without that field retain their historical full-close behavior.

Use lightweight continuity when the next planned item promptly continues in the same subsystem, domain, framework area, or implementation stream and risk remains bounded. Record a coherent local checkpoint, focused validation, clean tree, concise status/exit report, current handover, unresolved findings, inherited dependencies, rollback point, pending publication inventory, explicit Architecture disposition boundary, and no Engineering self-acceptance.

Lightweight continuity normally skips repeated standalone export, remote publication, semantic release, packaging, manifests/checksums, snapshots, exhaustive archival, broad detached validation that will immediately repeat, repository-wide conformance, and ceremonial reporting.

Select or strongly consider full closure for a phase or milestone close, ownership/domain change, delayed next item, external rollout/consumer/package dependency, compatibility boundary, irreversible recovery need, security/privacy/rights/integrity isolation, unclear accumulated unpublished work, unclear rollback, stale/fragmented evidence, repository divergence, or explicit user request. Three accumulated continuity items is an advisory review point, never an automatic override of risk or recoverability.

Related canonical Dual Hat changes may accumulate without rerelease. Each lightweight closeout inventories retained prior changes, current changes, expected semantic-version and compatibility impact, pending release notes, successor dependencies, and canonical source commit. Publish at the end of the related sequence, phase/milestone close, external need, package dependency, risk trigger, or explicit user request. Temporary deterministic local test packaging is not a release and must be contained and cleaned.
