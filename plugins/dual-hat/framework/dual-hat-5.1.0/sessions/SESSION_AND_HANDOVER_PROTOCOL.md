# Session and Handover Protocol

Every current session records operating mode, active role, work-item identity/type, lifecycle state, approved order hash, selected platform profile when one exists, current project-local model-tier mapping identity and environment fingerprint, and safe next transition. A fingerprint change marks the mapping stale and requires safe-boundary remapping before tier-dependent work resumes. Split transfers and Integrated safe-boundary mode changes use `schemas/mode-transition-package.schema.json`; context memory is never the transfer contract. The machine contract uses `active_work_item`, independently from `latest_completed_capability`; it may hold any governed registered type or `null`. Historical Capability-only records remain readable, but current generators must not overload them.

Exactly one current active-session record exists per governed repository. A repository may additionally maintain one current human/machine handover pair, and where it does, exactly one such pair exists; a repository whose active-session record carries the handover's content itself maintains none. Every governed record and pair is generated from repository truth and replaced on update; historical copies are retained only when policy requires them.

The active-session record is maintained throughout execution, not only at closure or switchover. Update it whenever a material goal, work item, lifecycle/role, authorization, repository/publication state, execution policy, gate, risk, or next action changes. A handover must never compensate for a stale active-session source by silently overriding it.

The repository's declared new-chat bootstrap artifact is the sole new-chat bootstrap input, and exactly one artifact holds that role. Where a repository maintains a handover pair, that role belongs to the current Markdown handover; where it does not, the role belongs to the active-session record's own rendered human-readable member, which must then carry a bootstrap instruction naming itself. The role is what binds, not the filename: a repository that folds its handover into its active-session record does not thereby lose the obligation, and a repository that retires the pair without moving the role leaves the protocol asserting an artifact that no longer exists. Do not create a separate continuation prompt, compatibility copy, or generated alias with overlapping authority. Other resume or interrupted-operation artifacts may exist only when they have a distinct bounded purpose and link back to the artifact holding the role.

The session records repository/product identity, current branch and commit, latest completed and active capability, phase/release state, authorization, protected assets, handover/snapshot freshness, unresolved decisions, waiting workflows, validation state, interruption recovery, and next allowed work.

The governed continuity surface -- the handover pair where one exists, and otherwise the active-session record -- records starting, implementation, corrected implementation, detached-validation, closure-evidence, generation-input, final published, and upstream commits without conflating roles. It also records worktree, external repositories, current snapshot, boundaries, risks, decisions, and stale/superseded handovers. Recording a commit role means stating what that role means and where its value is resolved from, which a record may satisfy without embedding the value: a resolved commit is true only at the instant it is written, and a surface that embeds one has asserted a claim it cannot keep current. A role whose value is deliberately not self-embedded is recorded, not omitted, and the two must stay distinguishable.

Free prose in the active-session record is admitted per entry, not per field. A field that accepts any string comes to narrate values other fields already hold, announce obligations no work item carries, and assert states that have since changed; detectors added afterwards can only guess from wording what a stored string was trying to be, and they err in both directions. So each prose entry declares the kind of claim it makes, from a vocabulary each section of the record admits for itself, and the declaration is bound to the entry so that editing one cannot leave the other stale. **A declared kind is a check, not a label.** It names what would show an entry of that kind false -- a lifecycle claim by the item's recorded state, a pointer to where a fact resolves by that artifact or command failing to resolve, a standing boundary by its cited authority, a narration of this session by the same text surviving from the record's previous value -- and a kind with no executable falsifier does not enter the vocabulary, since a vocabulary of labels constrains nothing that unlabelled prose did not. **A kind adds a check and never exempts an entry from one:** the checks that apply to every entry run whatever kind it declares, so relabelling to the kind with the weakest falsifier buys nothing. No kind admits a description of the record's own structure, standing guidance that does not expire with the session, a decision that has a record of its own, or a second copy of a value a field already holds.

Making a declaration mandatory on a surface rewrites the text that every other control parsing that surface reads, so each of those controls is a consumer of the change under [Governing Principles](../governance/GOVERNING_PRINCIPLES.md) principle 15 and is verified to read what it read before. The failure is quiet: a prefix added to satisfy one control makes another control's satisfying text unrecognisable, and the second control goes on demanding a declaration that is present and that it can no longer see -- an added obligation that silently removed one. Where two controls' requirements on the same text cannot both be met, the repair belongs in a control, never in rewording the entry. A parser serving a control distinguishes a declaration that is absent from one that is present but unreadable; a parser returning the same empty answer for both cannot report its own failure. The residual is that a mis-declared entry which passes its kind's falsifier is admitted: this raises the floor under what the record may hold and does not read intent, and prose that belongs elsewhere collects under whichever kind is cheapest to satisfy -- narration, in practice -- which is therefore the kind a reviewer of the record reads first.

Who is working an item is the dispatch inventory's to say ([Governing Principles](../governance/GOVERNING_PRINCIPLES.md) principles 6 and 8), and the record presents that answer rather than restating it. **An item shown in progress says who holds it.** Where the primary role may execute an item itself as well as delegate it, one in-progress status for both makes an item with no worker behind it indistinguishable from one left behind when its worker ended, and the human reader's plainest check -- is anyone actually on this -- becomes a question to the session instead of a reading. So the record marks an item held by the primary role's own execution distinctly from one a registered worker holds, from facts it already carries. It does not label every delegated item by elimination, which would copy the inventory into a second place, and it does not solve the ambiguity by forbidding self-execution or hiding such items, because an item being worked is the one its reader most needs to see. The residual: the marking says who holds an item, not whether the work is advancing, and a self-execution claim nobody has refreshed reads exactly like a fresh one unless the record also expires it.

**Prose about delegated work states policy, never inventory state.** A capacity, the condition it is tied to and its authority stay true until someone changes them; a count of live workers, or a sentence saying some are running or none are, is a second copy of the inventory -- true when written, read later as current, and costliest when it has gone stale in the direction that claims activity, which reads as progress and draws no investigation. A record whose inventory is verified empty while its prose asserts live work is refused where it is written. The residual: a check that recognises such an assertion by its wording refuses only the phrasings it recognises, and it says so where its clean result is read, so that a clean result is never taken to cover every phrasing or both directions of disagreement.

Every governed pair's Markdown and JSON must be semantically equal, schema-valid, current-path-valid, and generated from declared inputs. Update after capability closure, remediation, publication correction, phase/release change, branch/authority change, or protected-state change. Validation detects a stale fingerprint, contradictory pair, multiple active pairs, multiple artifacts claiming the new-chat bootstrap role, and hidden reliance on previous chat memory.

After interruption, verify live Git and external state, inspect owned child processes, recover only from committed or explicitly registered temporary state, and refresh bounded context before continuing. Session cleanup removes stale execution residue and marks abandoned work honestly.

A handover, a bootstrap prompt, a recovered scratch handoff, or a record written by another agent or before a gap is a set of claims, not an authority. Each operative claim is reconciled against live state before it is acted on, covering ownership, pending decisions, evidence counts, process state, and freshness. Work-item identity is namespace, identifier, and title or purpose, together with provenance and chronology, compared as a set; an identifier hit alone never counts as reconciled. A material discrepancy is reported with a conservative disposition before any assurance, commit, publication, or takeover of the affected work, and ambiguous ownership, completeness, or safety state preserves the evidence and defers the foreign lane rather than adopting it.

Refreshing bounded context after any interruption that can lose conversation memory -- context compaction chief among them -- requires reading the current active-session record's own state sections in full, not relying on a prior summary of it or on a partial earlier read. A context-loss summary is lossy by construction and must never be trusted as a substitute for the active-session record it was generated alongside; the record, not the summary, is authoritative. Before treating any tracked item's own status or lifecycle field as current, cross-check it against the actual repository history for a matching completion commit -- a status field can lag genuinely completed work, and lagging status is not itself evidence that the work remains undone.

## Chat switchover

The exact trigger phrase `Ready to switch chats.` requests a governed chat switchover. Continue to the nearest safe, low-ambiguity boundary without pausing healthy background work merely to prepare the handoff. At that boundary, classify and reconcile every in-flight task, delegated agent, owned process, mutation, and review. Take a fresh authoritative snapshot at the actual handoff time; never construct the handoff from stale or assumed state.

First verify and, when needed, refresh the active-session record. Then regenerate and validate the compact current-project handoff artifact under the repository's declared handoff authority and provide a minimal copyable bootstrap instruction that directs the new chat to read, verify, and follow that artifact. The artifact—not the bootstrap instruction—contains:

- the full active goal and exact current counters or state;
- authoritative repository paths;
- relevant commits, branch/upstream state, and worktree ownership, including unrelated or concurrent mutations that must be preserved;
- healthy background execution and its ownership, identity, continuation state, and stop conditions;
- pending gates, reviews, decisions, risks, and the exact next actions; and
- standing interaction, authority, publication, and protected-state rules needed to continue safely.

Explicitly tell the user when it is safe to switch. If a clean boundary cannot be reached promptly, identify the live item preventing it and provide the safest available handoff with the ambiguity, preservation rule, and next verification action made explicit. A switchover request is not authority to cancel work, terminate processes, alter publication state, or broaden scope.

The switchover gate fails closed when the active-session source is stale, the handoff input fingerprint is stale, required live-execution or review continuity is missing, Markdown and machine companion disagree, or another artifact claims overlapping new-chat authority.
